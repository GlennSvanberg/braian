## Setup

- Hardware: the same VPS as v3. AMD EPYC-Rome, 8 vCPU, 15.6 GB RAM. Everything ran on this one box: the load generator, Postgres, Redpanda, Typesense and the Braian processes.
- Isolation: separate containers with fresh credentials.
  - Postgres 18 (`wal_level=logical`, the same `-c` flags as the demo) on :5533
  - Redpanda on :29092
  - Typesense 30.2 on :8208
  - API :9190, relay :9191
  The demo DB was never touched. Demo `/healthz` was sampled every 5 s through every run and returned 204 every time.
- Data: synth medium tier.
  - Each object has 301 attributes and 10 languages, about 25 KB, stored as 13 value parts.
  - Budget `--searchable 10 --filterable 5 --sortable 2`.
  - 12 loaders, chunk 250, binary COPY, indexer defaults 200/100/4.
  - Database size after 10k objects: 170 MB, of which `object_values` is 151 MB.
- Two probe paths.
  - **Bench probes** (`perf-load`'s own, the same method as v3) send PATCH through an embedded router that has no search client. They measure the relay → Redpanda → indexer path only.
  - **API client** (`probe.py`) works the way the UI does, against the real `braian api` on :9190, which has write-through. Each probe does GET, then PATCH, then polls `/v1/search` every 25 ms until the hit appears, then GETs `/v1/objects/{id}/changes`. It also times the SSE event on `/v1/stream`.
  - Phases: **write** = during the bulk COPY; **backlog** = after the COPY while the indexer catches up; **idle** = after indexing is done.
- `/subscribe` does not exist. The SSE endpoint is `/v1/stream`.

## How close to instant

- **Interactive edits are now effectively instant in the UI.** The write-through puts an edit in search in about 65 ms when idle and about 0.2–0.4 s p95 even during a 50k COPY. SSE arrives in about 20 ms.
  - This is 5–20× better than v3, and the 5 s target is beaten by more than 10×.
  - The relay-only path is also 2–6× better, because the interactive and bulk lanes now flush separately.
- **Bulk is close but not there:**
  - 4.2k obj/s end to end, about 40% better than v3.
  - 5.1k obj/s with pregenerated data. The store itself meets 5000; synthetic generation on the same 8 cores is the remaining gap.
  - But **bulk searchability is not instant.** 50k objects take about 115 s to be fully indexed, because Typesense on one core does about 440–490 docs/s.

## Regressions

- **GET by id is about 2 ms slower** (7.1 → 9.1 ms p50) and PATCH→GET also rose by about 2 ms. This is probably the `DISTINCT ON (object_id, part) ... ORDER BY version DESC` latest-value read from V7.
- **Indexing throughput fell 5–8%** (516 → 490 docs/s at 10k).
- Read of 100 full objects is unchanged.

## Bottlenecks

1. Typesense indexing at about 500 docs/s on one core. This sets how long a bulk load takes to become searchable.
2. Bulk CPU contention on 8 shared vCPUs. Data generation costs about 17% (pregenerated 5086 vs 4237).
3. Interactive latency during a heavy COPY is CPU contention: PATCH p95 rises from 27 to 229 ms and SSE p95 from 28 to 215 ms.
4. Heavy search polling slows the relay path. The API client polled every 25 ms, and with it running the bench p95 rose from 0.7 to 2.5 s at 50k. The probes now share Typesense's single core with the indexer.
